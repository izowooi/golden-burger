GOLDEN KIWI · MICRO-CASCADE

5분짜리 군집 행동은
한 시간 더 이어지는가?

3~5회의 작고 연속적인 YES 상승을 사회적 정보 cascade의 후보로 보고, 이후 60분의 실행 가능한 호가에 움직임이 남는지 검증하는 네 팔 연구다. 현재는 수익 전략이 아니라, 단순하고 반증 가능한 심리 가설을 계측하는 simulation 전용 도구다.

RESEARCH / SIMULATION ONLY LIVE SOURCE-LEVEL HARD BLOCK 5분 cadence 4-arm preregistration $5 가상 진입
실거래 금지 — OOS에서 네 팔 모두 FAIL

uv run polybot run --live는 의도적으로 실패한다. 사전 등록한 외부표본 검정에서 primary B를 포함한 모든 팔이 승격 기준을 통과하지 못했으므로, private key나 funder address를 이 전략에 주입하지 않는다. 30일 검정을 통과하더라도 바로 live가 되는 것이 아니라 별도 shadow execution review만 열 수 있다.

어디서 나온 전략인가

Lime·Fig·Mango·Date·Honeydew·Nectarine 여섯 폐쇄 전략의 DB와 로그를 함께 검토한 통합 포스트모템에서 출발했다. 실패한 threshold를 합쳐 “최고 전략”을 만든 것이 아니라, 반복하면 안 될 회전율·표본 선택·체결 증거·event 의존 문제를 코드 제약으로 제거하고 작은 연속 상승의 지속성이라는 독립 가설 하나만 남겼다.

전략을 한글로 풀면

관찰
  5분 안팎으로 YES 가격을 계속 저장한다.

후보
  표준 이진 Yes/No + YES 20~80% + 해결까지 6시간 이상
  + 유동성 $20,000 이상 + 24시간 거래량 $10,000 이상
  + 유효한 bid/ask + spread 2%p 이하

추세
  각 간격 3~10분
  + 3회 또는 5회 연속 상승
  + 각 상승은 0 초과 2%p 이하
  + 누적 상승은 팔별 1%p 또는 2%p 이상, 공통 최대 4%p

가상 진입
  같은 event에서 유동성이 가장 큰 하나를 고른다.
  event별 승자는 전체 유동성 내림차순·condition ID 오름차순으로 다시 정렬하고,
  그 순서에서 fresh gate를 처음 통과한 최대 1개/cycle만 진입한다.
  한 번의 fresh CLOB book에서 midpoint·bid·ask·spread·depth를 함께 고정하고
  마지막 step과 gap을 다시 확인한 뒤 $5 simulation을 기록한다.

가상 종료
  진입 60분 뒤 처음 실행된 cycle의 fresh best bid
  = hypothetical P&L일 뿐, 실제 fill이나 realized P&L이 아님

Primary 연구 outcome
  raw signal 전체에서 사전 순서로 고른 raw_selected의 point-in-time best ask
  → +60~75분 독립 condition 조회의 첫 SUCCESS valid best bid
  = 가상 position 수와 무관한 event-equal counterfactual

최근 24시간 거래량은 최소 유동성 gate로만 쓴다. 24시간 누적값의 증가를 짧은 추세 가속으로 해석하지 않는다. 정확한 5분 cadence에서는 명목상 15/25분이지만, 허용 gap 3~10분에서 실제 span은 3-step 9~30분, 5-step 15~50분이다. 가격 stop, take-profit, trailing stop도 두지 않아 네 팔의 비교창을 동일한 60분으로 고정한다.

공통 진입 계약

  1. Point-in-time evidence — 현재 snapshot은 아직 RUNNING인 run의 cursor-complete Gamma sweep에 연결되고, 이전 관측은 같은 cohort의 SUCCESS·cursor-complete row여야 한다.
  2. 표준 이진 시장 — outcomes가 정확히 Yes/No 두 개이고, 서로 다른 token 두 개이며 negRisk=false가 명시되어야 한다.
  3. 시간·가격·시장성 — 해결까지 6시간 이상(최대 horizon 상한 없음), YES [0.20, 0.80], liquidity ≥ $20,000, volume24h ≥ $10,000.
  4. 실행 가능 호가 — 0 < bid ≤ ask < 1, spread ≤ 0.02, $5 수량의 1.2배 ask depth를 fresh book에서 재확인한다.
  5. 시장군 제외 — exact tag sports, games, esports, crypto-prices, up-or-down, multi-strikes, 5m, 15m, 1h를 제외한다. 명시적 빈 tag 목록은 허용하지만 누락·비정상 tag metadata는 fail-closed한다. 스포츠 제외는 수익성 근거가 아니라 동질적인 연구 universe를 고정하기 위한 선택이다.
  6. event와 cycle 선택 — 한 collecting run에서 event당 유동성 1위 condition 하나만 고른다. event별 승자는 전체 유동성 내림차순·condition ID 오름차순으로 정렬하고 fresh gate를 처음 통과한 최대 1개만 진입한다. 같은 event의 재진입은 6시간 뒤에 허용한다.
진입 밴드 밖의 lineage가 잘리지 않도록 archive는 YES [0.16, 0.84]를 저장한다. Gamma fetch의 서버측 유동성 하한은 $1,000이며, 이 아래에서 $20,000 entry gate로 급등한 시장은 새 3/5-step lineage가 쌓일 때까지 backfill 없이 제외한다. 각 snapshot에는 전체 sweep 종료시각이 아니라 해당 Gamma page의 로컬 수신시각을 쓴다. 60일 동안 실제 5분 원본을 보존하며 cold rollup을 5분 data로 해석하지 않는다.

정확한 2 × 2 네 팔

다른 값은 모두 고정하고 연속 상승 횟수와 누적 상승 하한 두 축만 바꾼다. 결과가 좋아 보이는 팔을 사후에 primary로 바꾸지 않는다. 무처치 control이나 동일 시장의 무작위 배정 실험은 아니며, B만 confirmatory primary이고 A/C/D는 희귀성·threshold 민감도·반증용 비교군이다.

독립 재검토 정정: C의 유일한 양수 신호는 서로 다른 Git commit의 snapshot을 한 계단으로 이은 계약 위반이었다. 과거 Honeydew DB도 관측 당시의 outcomes/token/tags/negRisk를 snapshot별로 고정하지 않아, 위 A/B/C/D 수치는 현재 기준의 promotion evidence가 아니다. C의 +0.5263% 해석은 철회한다. Immutable 과거 산출물은 감사용으로 보존하며, primary B의 표본·CI gate 실패와 live 금지 결론은 변하지 않는다.

새 수집에서는 현재 run의 마지막 row와 같은 config_hash × git_commit × mode × job_name인 SUCCESS/cursor-complete history만 lineage로 쓴다. 이 값은 top-of-book 반사실이며 depth, queue, latency, partial fill, fee를 증명하지 않는다.

Jenkins 수집 계약

  • 각 job의 Build periodically에 trigger를 입력하고 숨은 H offset을 쓰지 않는다. A/B/C/D trigger를 각각 0-59/5 * * * *, 1-59/5 * * * *, 2-59/5 * * * *, 3-59/5 * * * *로 고정한다.
  • Execute concurrent builds if necessary를 끈다. 한 job의 DB에는 writer가 하나만 있어야 한다.
  • canonical job 이름을 그대로 --job에 전달한다. 각 DB는 data/<job>/trades_sim.db로 분리된다.
  • 네 팔은 같은 Git commit과 정확히 같은 30일 UTC 반개구간을 쓰고, arm별 POLYBOT_CADENCE_OFFSET_MINUTE는 0/1/2/3으로 고정한다.
  • workspace가 모노레포 루트인지, Jenkins agent에서 예시의 /Users/jongwoopark/.local/bin/uv가 실제 경로인지 확인한다.
  • trigger 활성화 전에 polybot config를 수동 실행해 arm, job, offset, 절대 DB 경로와 Promotion collection: ENABLED를 확인한다.
  • 실험 시작·종료·offset 세 환경변수가 없으면 smoke/archive mode이고 collection_eligible=0이다. 일부만 설정하면 시작을 거부한다.
  • wallet credential은 필요하지 않다. private key, funder address, signature type을 Kiwi job에 주입하지 않는다.
  • 회고에서는 실제 SUCCESS run과 3~10분 lineage gap만 인정하며, 기대 5분 slot coverage가 90% 미만이면 평가 불가로 판정한다. 정규 slot 밖이나 같은 slot의 중복 SUCCESS run이 하나라도 있으면 그 run의 signal·follow-up을 제외하고 promotion도 fail-closed한다.
#!/bin/bash
set -euo pipefail

export LOG_LEVEL=INFO
export POLYBOT_CONFIRMATION_STEPS=3       # A/B=3, C/D=5
export POLYBOT_MIN_CUMULATIVE_MOVE=0.02   # A/C=.01, B/D=.02
export POLYBOT_EXPERIMENT_START_UTC=<확정할_UTC_START>
export POLYBOT_EXPERIMENT_END_UTC=<START의_정확히_30일_뒤>
export POLYBOT_CADENCE_OFFSET_MINUTE=1    # A/B/C/D = 0/1/2/3

cd ./golden-kiwi
/Users/jongwoopark/.local/bin/uv sync --frozen
/Users/jongwoopark/.local/bin/uv run polybot config --job kiwi-sim-b-3x2
/Users/jongwoopark/.local/bin/uv run polybot run --simulate --job kiwi-sim-b-3x2

위 예시는 primary B다. 정확한 30일 구간은 첫 실행 전에 사용자가 확정해야 한다. A/C/D에서는 두 처치값, canonical job과 offset만 표에 맞게 바꾼다. 한 cycle의 p95가 5분을 넘거나 gap이 지속적으로 3~10분을 벗어나면 threshold를 느슨하게 하지 않고 해당 cohort를 cadence 실패로 분류한다.

30일 뒤 판정 — 통과해도 shadow review뿐

네 DB의 독립 UTC 기간을 사전에 고정한다. Primary B가 아래를 모두 만족해야 다음 단계 검토를 열 수 있다.

  1. quote-complete signal 50개 이상, unique event cluster 30개 이상
  2. event-cluster Bonferroni 98.75% lower confidence bound가 0보다 큼
  3. 추가 10.4bps stress 후에도 같은 lower bound가 0보다 큼
  4. 사전 정의한 전반부와 후반부가 모두 양수
  5. target/quote coverage 90% 이상
  6. 충분히 표본이 있는 config_hash × git_commit × mode × job_name cohort에서 material sign reversal 없음
  7. 60일 raw 5분 archive·run/sweep/catalog/lineage evidence 충족
  8. strict retro audit의 CRITICAL/HIGH가 0

Primary metric은 append-only raw signal 전체에서 사전 고정 순서로 선택된 raw_selected의 point-in-time best ask와, +60~75분 사이 독립 condition 조회에서 처음 얻은 SUCCESS-run valid best bid를 비교한다. simulation position 결과는 별도 diagnostic이다. 네 DB 각각의 exact-window strict audit JSON이 없거나, audit의 database_sha256과 분석 DB 실제 바이트가 다르거나, immutable contract·cadence·cohort 증거가 불완전하면 NOT_EVALUABLE_FAIL_CLOSED다.

판정의 상한: 모두 통과해도 실제 주문 승격이 아니다. $5 depth와 latency, BUY/SELL exact confirmed full fill, fee와 maker/taker role, partial/zero/unknown fill, reconciliation을 계측할 별도 shadow execution review만 허용한다. B가 실패하거나 50/30 표본을 못 채우면 threshold를 완화하지 않고 STOP / UNRESEARCHABLE로 끝낸다.
