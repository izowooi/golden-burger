🫐 Golden Blueberry

Closing Surge

해결 또는 경기 종료까지 72시간 이내인 표준 이진 시장에서 YES가 0.85를 처음 상향 돌파할 때 진입한다. 과거 Cherry의 아이디어를 수익 전략으로 단정하지 않고, $5 exact-fill 실거래 두 팔로 다시 검증한다.

진입 0.85–0.93A 2%p · B 5%p 익절 0.97 · 손절 0.78스포츠 경기 중 포함 $5 × 두 계정 · 총 $300

한눈에 보는 규칙

진입 = strict standard binary YES, negRisk=false + 저장된 직전 YES < 0.85 ≤ 현재 YES ≤ 0.93 + 0분 < 연속 snapshot 간격 ≤ 15분 + 보존기간 안에서 앞선 YES ≥ 0.85 관측 없음 + 상승폭 ≥ 0.02(A) 또는 0.05(B) + 일반/경기 전: 0시간 < 남은 시간 ≤ 72시간 + 스포츠 경기 중: kickoff 후 ≤ 360분 + 유동성 ≥ $10,000, 24h 거래량 ≥ $10,000 + fresh ask ≤ 0.93, spread ≤ 0.02, ask depth ≥ 주문수량 × 1.20 청산 = 미해결 YES ≥ 0.97 AND fresh bid ≥ 0.97 OR 미해결 YES ≤ 0.78 없는 규칙 = trailing stop, 임의 time exit 별도 사실 = resolution, redeem/현금화, CLOB SELL fill
스포츠는 기본 포함됩니다. gameStartTime을 경기 종료가 아니라 경기 시작 시각으로 해석한다. 따라서 경기 전 72시간뿐 아니라 upstream이 거래 가능 상태인 경기 중 첫 급등도 kickoff 후 360분까지 살 수 있다.

과거 전략에서 확인된 것과 확인되지 않은 것

확인된 역사

초기 Banana 계열은 2026-02-04에 24시간 집중 규칙과 스포츠 포함을 거쳤고, 다음 날 12–720시간으로 확장됐다. 현재 그 계보는 golden-cherry에 가깝다.

확인되지 않은 수익

Cherry 사본에는 legacy 체결 공백이 크고 실제 fee까지 완결된 표본이 부족하다. 운영자가 기억하는 “월 10%”를 현재 DB로 재현하거나 반박할 수 없다.

확인된 스케일 위험

$8,000 cohort에서 주문액/표시 유동성이 평균 57.64%였다. 체결 실패와 시장충격을 무시한 급격한 증액은 같은 전략이 아니다.

Blueberry의 대응

$5 hard cap, event당 1건, actual depth, exact fill, rejected crossing, source digest와 resolved config를 모두 남긴다.

Blueberry도 아직 edge가 입증되지 않았습니다. 비슷한 golden-melon은 24시간 거래량 floor를 세 팔로 비교한다. Blueberry는 거래량을 $10,000으로 고정하고, 사용자가 말한 “확률이 얼마나 치솟아야 하는가”만 2%p 대 5%p로 검증한다. 두 실험 결과를 섞어 승률을 만들지 않는다.

왜 $1이 아니라 $5인가

주문액0.93에서 받는 수량판정
$11.08 shares5-share CLOB 최소 주문 미달
$55.38 shares5.0 + 0.1 안전 buffer 충족

$5는 공격적인 금액이 아니라 이 진입 밴드에서 가능한 최소 notional이다. 각 arm에 $150를 배정해 총 $300을 사용하되, 동시에 여는 금액은 arm당 최대 $50이고 경제손익이 −$30이면 신규 BUY를 코드가 차단한다.

나머지 진입·청산·실행완전히 동일

두 job은 같은 날 시작하고 같은 snapshot 시각을 보도록 */5 * * * *, concurrent build 금지를 쓴다. job마다 분 offset이 달라지는 H/5는 사용하지 않는다. 코호트는 config_hash × strategy_source_digest × mode × job_name으로 구분한다. Git commit은 provenance일 뿐 실험을 고정하는 핀이 아니다.

Freestyle Jenkins shell

#!/bin/bash
set +x
set -euo pipefail

# 두 secret은 Jenkins Credentials Binding으로 주입
export POLYMARKET_SIGNATURE_TYPE=3  # legacy 계정은 1
export LOG_LEVEL=INFO
export POLYBOT_LIFECYCLE_MODE=active
export POLYBOT_BUY_AMOUNT=5
export POLYBOT_EXPERIMENT_CAPITAL_USDC=150
export POLYBOT_MIN_SURGE=0.02       # B만 0.05

: "${POLYMARKET_PRIVATE_KEY:?Credentials Binding required}"
: "${POLYMARKET_FUNDER_ADDRESS:?Credentials Binding required}"

cd ./golden-blueberry
/Users/jongwoopark/.local/bin/uv sync --frozen
/Users/jongwoopark/.local/bin/uv run polybot config --live \
  --job blueberry-live-a-2pp
/Users/jongwoopark/.local/bin/uv run polybot run --live \
  --job blueberry-live-a-2pp

B는 0.05와 blueberry-live-b-5pp만 바꾼다. 저장소 기본은 simulation이며 실제 주문은 --live를 명시해야 한다.

1주와 30일에 무엇을 판단하나

  1. 1주: 수익으로 승자를 고르지 않는다. 5분 주기, sweep 완전성, first-crossing 저장, source/config 고정, BUY/SELL fill·fee coverage, backup을 점검한다.
  2. 30일: arm당 confirmed closed 20건 이상일 때만 비교한다. actual net P&L, win rate, 후보→주문→체결 attrition과 손실 꼬리를 함께 본다.
  3. 부족하면: 임계값을 중간에 바꾸지 않고 기간을 연장하거나 INCONCLUSIVE로 끝낸다.
  4. 증액: 먼저 $5에서 증거 계약을 통과한 뒤 별도 reviewed cohort로만 $10 → $20처럼 단계적으로 올린다. 환경변수만으로 hard cap을 우회할 수 없다.

읽기 전용 분석기는 두 arm의 공통 설정이 최소 상승폭 외에는 같은지, DB와 job이 분리됐는지, source digest와 fee coverage가 완전한지 먼저 검사한다. 조건을 통과해도 자동 승자를 선언하지 않는다.
