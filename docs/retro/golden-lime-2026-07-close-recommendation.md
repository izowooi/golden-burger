## 2. 진단 — 무엇이 왜 망가졌는가

(각 항목의 수정 가능 여부는 §5 참조. 구현 결함은 대부분 고쳐졌다.)

### 2-1. 신호가 "충격"을 감지하지 않는다

`signals.py:153`:

```python
base = min(p.price for p in window)     # 6시간 윈도우의 최저가
jump = current_price - base
if jump < jump_min - EPSILON: return None
```

기준점이 윈도우 **최저가**다. 즉 "현재가가 6시간 범위의 최저점보다 0.10 위에 있다"는
조건이며, **사건이 있었는지와 무관하다.** 폭 0.11짜리 박스권에서 위쪽을 칠 때마다
매번 "급변"으로 판정된다. 최저값은 순서통계량이라 노이즈가 클수록 낮아지므로,
변동성이 큰 시장일수록 신호가 더 자주 뜬다.

여기에 `max_pullback` 게이트가 겹친다 — `signals.py:184`:

```python
return (peak - current_price) <= max_pullback + EPSILON   # 0.02, 절대 확률 포인트
```

60분 고점 대비 0.02 이내. 두 조건을 합치면 **"6시간 최저가보다 0.10 위이면서 동시에
1시간 최고가 바로 밑"** — 이건 국소 최고점의 정의다. 전략 이름과 달리 충격 편승이 아니라
**구간 천장 매수**다. `STRATEGY.md:119`가 실패 시나리오 1번으로 예견한 바로 그 상태다.

> 참고: `max_pullback: 0.02`는 2%가 아니라 **2 확률 포인트**다. 상대 기준으로는
> 진입가 0.25에서 8.0%, 0.85에서 2.4%로 4배 가까이 달라진다. 진입 게이트는 절대값,
> 청산 게이트는 상대% — 밴드 양끝에서 사실상 다른 전략이 된다.

### 2-2. 실행 방식이 가설과 논리적으로 모순된다

`trader.py:102, 147-152`:

```python
current_price = self.clob.get_midpoint(token_id)
result = self.clob.place_limit_order(token_id=..., price=current_price, side="BUY")
```

→ `clob_client.py:483` `post_order(signed_order, OrderType.GTC)`

모멘텀 편승은 **즉시성**이 생명인데, 구현은 midpoint에 **수동적 GTC 지정가**를 걸고 기다린다.
이 주문이 체결되려면 **누군가 그 가격에 나에게 팔아야** 한다.

- 상승이 실제로 이어지면 → 호가가 위로 도망가서 **체결되지 않는다**
- 상승이 꺾여 매도가 나오면 → **체결된다**

**가설이 맞을수록 체결이 안 되고, 틀릴수록 체결된다.** 체결된 표본은 구조적으로
"모멘텀이 끊긴 케이스"에 치우친다. 이것은 역선택이다. 기존 파라미터로는 손댈 수 없었고, §5에서 `POLYBOT_ENTRY_PRICE_MODE=ask`로
해소했다.

### 2-3. 상승은 확률이 아니라 경로 때문에 도달 불가

`trader.py:177`에서 `max_price=current_price`(=매수가)로 초기화된다. 따라서
트레일링 -6%가 손절 -8%보다 **항상 먼저** 걸린다. 실효 리스크 한도는 -6%다.

익절까지 필요한 추가 상승폭:

| base | 진입가 | 익절 목표(×1.12) | 추가 필요 | 원 점프(0.10) 대비 |
|---|---|---|---|---|
| 0.15 | 0.25 | 0.280 | +0.030 | 30% |
| 0.30 | 0.40 | 0.448 | +0.048 | 48% |
| 0.50 | 0.60 | 0.672 | +0.072 | **72%** |
| 0.70 | 0.80 | 0.896 | +0.096 | **96%** |

base 0.70이면 익절가가 0.896인데, **정작 전략은 0.85를 넘으면 매수를 거부한다**
(`current_max`). 자기가 "너무 비싸다"고 판단하는 가격까지 가야 이익이 난다.

그리고 그 길을 **한 번도 되돌리지 않고** 가야 한다. 진입 0.40 기준:

- 익절까지 **+4.8¢**
- 트레일링 여유 **2.4¢** (틱 0.01, midpoint는 0.5¢ 단위 → 약 5스텝)
- 5분마다 검사

즉 승률이 문제가 아니라 **경로 조건**이 문제다.

### 2-4. (동반) momentum_death가 진입 직후부터 무장된다

`signals.py:313`: `return (current_price - window[0].price) <= 0.0`
— "3시간 전보다 높지 않으면 청산".

`bot.py:129`가 매 사이클 **universe 전체**에 snapshot을 적재하므로, 방금 산 시장도
이미 3시간치 이력이 있다. 그래서 `signals.py:302`가 주장하는 "매수 직후 즉시 청산 방지"
가드는 작동하지 않고, **매수 5분 뒤 첫 매도 검사부터 무장된다.**

게다가 거래량 게이트가 쓰는 `volume24hr`는 24시간 **누적**이라 점프 몇 시간 뒤에야
2배를 충족한다. 그 시점엔 "3시간 전 가격"이 이미 점프 후 가격이므로,
**횡보만 해도 즉시 청산**된다. `STRATEGY.md:120`이 실패 시나리오 2번으로 예견했다.

## 4. 청산 구조는 수학적으로 edge가 0이다

무편향 가격에서 위 장벽 a·아래 장벽 b에 대해 `P(위 먼저) = b/(a+b)`이고,
손익분기 승률도 **정확히 같은 값**이다.

| 설정 | P(익절 먼저) | 손익분기 승률 | EV |
|---|---|---|---|
| TP+12 / SL-8 | 40.0% | 40.0% | **0** |
| TP+12 / 트레일링-6 (실효) | 33.3% | 33.3% | **0** |
| TP+20 / SL-8 | 28.6% | 28.6% | **0** |

**TP/SL을 어떻게 조합해도 EV가 정확히 0이다.** 수익은 오직 실제 표류(모멘텀)에서만
나올 수 있고, 그 위에 트레일링(승자 절단), 수수료·스프레드(`grep -rn "fee" src/` → 0건,
즉 계산에 아예 없음), 전손 가능성이 얹힌다.

전손이 섞이면:

| 전손 비율 | 필요 승률 |
|---|---|
| 0% | 40.0% |
| 5% | 63.0% |
| 10% | **86.0%** |
| 13% 이상 | **불가능** |

## 5. 파라미터·코드로 고칠 수 있는가 — 항목별 판정

초판에서 §2-1·§2-2를 "수정 불가"로 적었으나 **부정확했다.** 둘 다 작은 코드 변경으로
해결 가능하며, 2026-07-28에 **기본값을 바꾸지 않는 opt-in 플래그로 구현했다.**

| 문제 | 수단 | 상태 |
|---|---|---|
| 포지션 무제한 (§3) | `POLYBOT_MAX_POSITIONS=N` | ✅ 기존 env |
| 트레일링이 승자 절단 (§2-3) | `POLYBOT_TRAILING_STOP_ENABLED=false` | ✅ 기존 env |
| momentum_death 조기 발동 (§2-4) | `POLYBOT_DEATH_WINDOW_HOURS` + 가드 버그 수정 | ✅ **코드 수정 완료** |
| base가 윈도우 최저가 (§2-1) | `POLYBOT_JUMP_BASE_MODE=open` | ✅ **신규 구현** |
| 수동적 지정가 체결 (§2-2) | `POLYBOT_ENTRY_PRICE_MODE=ask` | ✅ **신규 구현** |
| 익절이 점프의 30~96% 추가 요구 (§2-3) | `POLYBOT_TAKE_PROFIT` 하향 | △ 하향해도 EV=0 유지 (§4) |
| 청산 구조의 EV=0 (§4) | — | ❌ **수단 없음** |
| 가설 자체가 인용 리서치와 반대 | — | ❌ **수단 없음** |

### 구현한 코드 변경 (기본값은 기존 동작 유지)

1. **`POLYBOT_JUMP_BASE_MODE`** (`min` 기본 | `open`)
   `signals.py:detect_jump`. `open`은 윈도우 **시작가** 대비 순변화만 점프로 인정한다.
   폭 0.12짜리 박스권을 왕복하고 제자리로 온 구간은 `min`에서 점프로 잡히지만
   `open`에서는 걸러진다 (`tests/test_signals.py`에 경계 테스트 4건 추가).

2. **`POLYBOT_ENTRY_PRICE_MODE`** (`midpoint` 기본 | `ask`)
   `trader.py`. `ask`는 best ask에 걸어 즉시 체결을 노린다. §2-2의 "가설이 맞을수록
   체결 안 됨" 문제를 해소한다. 대신 스프레드를 매번 지불한다.

3. **momentum_death 가드 버그 수정** (플래그 없음, 무조건 적용)
   `trader.py:_is_momentum_dead`. 보유 시간이 `death_window_hours`에 못 미치면
   판정을 보류한다. 기존에는 snapshot이 universe 전체에 쌓이는 탓에
   `signals.py:302` docstring이 의도한 가드가 무력화되어 매수 5분 뒤부터 청산이
   발동했다.

4. 두 모드는 `main.py config` 출력과 매 사이클 로그에 표시된다(적용 여부 확인용).

**그러나 이것을 모두 적용해도 §4의 barrier math로 EV는 0이고**, 이 전략이 인용한
유일한 리서치(`STRATEGY.md:20`)는 **"10%+ 급변은 mean-revert"** 라고 말한다.
코드 수정은 "가설을 공정하게 시험할 수 있는 상태"를 만들 뿐, 가설을 참으로 만들지 않는다.

## 5-1. 그래도 한 달 더 돌린다면 — 실행 가능한 설정

폐쇄가 권고이지만, 사용자가 검증을 원할 경우의 최선 설정이다.

```bash
# ── 리스크 (근거 있음, 반드시 적용) ──────────────────────
export POLYBOT_MAX_POSITIONS=5            # -1(무제한) → 5
export POLYBOT_BUY_AMOUNT=5

# ── 청산 (근거 있음) ────────────────────────────────────
export POLYBOT_TRAILING_STOP_ENABLED=false  # 승자만 자르므로 순수 마이너스 (§2-3)
export POLYBOT_DEATH_WINDOW_HOURS=12        # 3 → 12. 조기청산 완화 (§2-4)

# ── 신호·실행 (신규 구현) ───────────────────────────────
export POLYBOT_JUMP_BASE_MODE=open          # 박스권 천장 매수 차단 (§2-1)
export POLYBOT_ENTRY_PRICE_MODE=ask         # 즉시 체결 (§2-2)

# ── 아래는 백테스트로 정할 것. 임의값을 쓰지 말 것 ────────
# export POLYBOT_JUMP_MIN=?
# export POLYBOT_MAX_PULLBACK=?
# export POLYBOT_VOL_MULT_MIN=?
```

**`JUMP_MIN`·`MAX_PULLBACK`·`VOL_MULT_MIN`에 임의의 숫자를 제안하지 않는다.**
근거 없이 55% 승률 기준을 복사해 쓴 것이 이 전략의 원래 실수였다(§6-4).
`tools/lime_jump_backtest.py`가 이 세 값의 격자를 스윕해 각 조합의 사후 수익률을
내므로, **측정한 뒤 정한다.**

### 치명적 제약: 계좌에 여력이 없다

현재 $66.36 중 $63.68이 이미 포지션에 묶여 있고 **가용 현금은 $2.68**이다.
`buy_amount_usdc: 5.0`이므로 **신규 진입이 한 건도 불가능하다.**

즉 5-1을 실제로 시험하려면 **추가 입금이 필요하다.** §4(EV=0)와 §6(가설이 인용
리서치와 반대, 백테스트 없음)을 고려하면, 검증되지 않은 가설에 신규 자본을 넣는
결정이 된다. §7의 백테스트를 먼저 돌려 근거를 확보한 뒤에 판단할 것을 권한다.

## 6. 절차상 문제 (재발 방지용 기록)

1. **백테스트 artifact가 존재하지 않는다.** `new-strategy-playbook.md:29`가 요구하는
   재실행 가능한 독립 artifact가 없다.
2. **자기가 정한 시뮬레이션 단계를 건너뛰었다.** `STRATEGY.md:128`은 실전 전
   **1~2주 `--simulate`** 를 요구하는데, Jenkins는 `main.py run`(플래그 없음)으로
   바로 실전이었다.
3. **손실 기반 폐기 기준이 없다.** 유일한 폐기 게이트(`momentum_death` 비율 >50%)는
   "4주 후, 30+ 거래" 조건이 붙어 있어 14일 -72%에도 울리지 않는다.
   `new-strategy-playbook.md:15`가 요구하는 **최대 낙폭 사전 등록**이 없다.
4. **승률 기준 55%가 유도 없이 복사됐다.** elderberry는 TP:SL 1:1이라 55%가 맞지만,
   lime은 1.5:1이라 손익분기가 40%다.

## 7. 이 결론을 뒤집을 수 있는 유일한 검증

lime은 `bot.py:129`에서 매 사이클 universe 전체 snapshot을 적재한다
(cherry는 호출부조차 없었다). 즉 **한 번도 수행되지 않은 백테스트를 사후에 할 수 있다.**

거래 표본(약 31건)이 아니라 **관측된 모든 점프 이벤트**(수백~수천)로 판정하므로
검정력이 비교가 안 된다. 도구는 작성·검증 완료:

```
scratchpad/lime_backtest.py   # 합성 데이터로 동작 검증 완료
```

필요한 것:
```
맥미니: /Users/jongwoopark/.jenkins/workspace/polybot-lime/golden-lime/data/default/trades.db
   ↓
이 맥: /Users/izowooi/git/t1/golden-lime/data/default/      (.gitignore:40 data/ 로 무시됨)
```

출력: `jump_min` 0.08~0.20 × `vol_mult` 0~3배 × `pullback` 2~10% 스윕에 대해
1/3/6/12/24/48시간 후 평균 수익률·중앙값·상승비율·t통계. 그리고 반대 방향
(급락 후 반등, elderberry 가설)도 같은 형식으로 낸다.

- **양의 표류가 나오는 영역이 있으면** → 폐쇄 보류, 그쪽으로 파라미터 이동
- **없으면** → 폐쇄 결정의 결정적 근거

snapshot 보존이 7일(`bot.py:72`)이므로 **DB를 지금 확보하지 않으면 이 검증은 영구히 불가능하다.**

## 8. 폐쇄해도 잃지 않는 것

`golden-elderberry`(Panic Fade)가 **정반대 가설**로 같은 급변 이벤트 클래스를 이미
커버하고 있고 정상 작동 중이다. 두 봇은 설계상 A/B 쌍이므로
(`golden-elderberry/STRATEGY.md:36`), 한쪽 가설이 틀렸다는 결론은 곧 나머지 한쪽의
근거가 된다. lime을 닫아도 이벤트 클래스 커버리지는 유지된다.

## 9. 폐쇄 절차

**1단계 — 즉시 (신규 진입만 차단, 청산은 유지)**

Jenkins 스크립트에 한 줄:
```bash
export POLYBOT_LIFECYCLE_MODE=close_only
```
`config.py:15`에 지원되는 모드다. 되돌리기도 한 줄이라 §7 검증 결과를 기다리는
동안 안전하게 유지할 수 있다.

**2단계 — 잔여 포지션 정리**

`tools/reconcile_positions.py`로 DB와 지갑을 대조한 뒤
(`--funder <lime 공개주소>`), 남은 실보유는 Polymarket UI에서 직접 정리하거나
해결까지 보유한다. 잔액이 $66 수준이라 청산 비용 대비 방치가 나을 수 있다.

**3단계 — job 정지**

Jenkins에서 `polybot-lime` job을 disable한다. 코드·DB는 삭제하지 않는다
(회고 자산). `REPOS.md`와 루트 `AGENTS.md`의 전략 인덱스에 폐쇄 사실을 기록한다.

## 10. 다른 전략에 적용할 교훈

lime 고유 문제가 아닌 것들이다. 다른 봇에서도 확인할 것:

1. **`max_positions: -1`을 쓰는 전략이 또 있다** — `golden-mango`
   (`docs/retro/golden-mango.md:69`가 "실전은 제한 권장"이라고만 적어둠). 실전 투입 전
   반드시 상한을 도출한다.
2. **매도 유령 포지션 핸들러 부재** — lime은 매수 유령(`_mark_unfilled`)은 처리하지만
   매도 유령은 처리하지 않는다. `trader.py:364`가 `orderID`만으로 `COMPLETED` 처리하고
   미체결 매도 주문을 취소하지 않는다. cherry에서 확인된 것과 같은 계열의 문제다.
3. **`EXPIRED`가 `realized_pnl=None`이라 `total_pnl` 집계에서 빠진다**
   (`trader.py:216`, `repository.py:199-201`). 봇의 자체 성적표가 최악의 거래를
   구조적으로 보여주지 못한다.
4. **모멘텀 계열 전략에 수동적 지정가를 쓰면 안 된다** (§2-2). 방향성 편승 전략은
   taker 체결이 전제다.
